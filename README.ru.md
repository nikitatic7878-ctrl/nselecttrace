# nselecttrace

[English](README.md) | [Русский](README.ru.md)

`nselecttrace` — небольшая кроссплатформенная CLI-утилита для просмотра сети и
диагностики.

Она отвечает на повседневные вопросы о сети машины: какие есть интерфейсы, какие
порты слушаются, какой процесс ими владеет, что сейчас соединено. Всё это — один
бинарник без внешних зависимостей во время работы и без вызова `netstat`, `ss`,
`nslookup` или `ping` через shell.

Это ранняя версия проекта. Это не сниффер пакетов, не сетевой сканер и не сервер
мониторинга. Это диагностический инструмент только для чтения: он показывает то,
что уже известно операционной системе, а для `dns` и `ping` выполняет одну
чётко очерченную сетевую операцию.

## Что такое nselecttrace?

- **Сначала локальный осмотр.** `interfaces`, `ports` и `connections` читают
  состояние самой машины и не обращаются к сети.
- **Ровно две сетевые операции.** `dns` выполняет прямой запрос, `ping`
  отправляет ICMP echo-запросы. Больше в сеть ничего не ходит.
- **Привязка к процессам.** В списках сокетов определяется владеющий процесс,
  поэтому слушающий порт связывается с программой, а не только с числом.
- **Системные API там, где это важно.** Перечисление сокетов в Windows
  использует IP Helper API (`GetExtendedTcpTable` / `GetExtendedUdpTable`), а не
  разбор вывода системной команды.
- **Только стандартная библиотека.** Внешних зависимостей нет вообще: бинарник
  компактный, а сборка воспроизводимая. ICMP реализован напрямую на пакете
  `net` языка Go, без подключения сетевой библиотеки.
- **Вывод, пригодный для обработки.** Результаты идут в stdout, предупреждения и
  ошибки — в stderr, поэтому таблицу можно спокойно передавать в другую
  программу через конвейер.

## Возможности

| Команда | Что делает |
|---|---|
| `interfaces` | Сетевые интерфейсы: состояние, MAC, адреса IPv4/IPv6 |
| `ports` | Слушающие и занятые TCP/UDP-сокеты с владеющим процессом |
| `connections` | Активные соединения с локальным и удалённым endpoint |
| `dns <host>` | Прямое DNS-разрешение в записи A и AAAA |
| `ping <host>` | Доступность по ICMP с временем отклика по каждому пакету |
| `about`, `version` | Информация о хосте, среде выполнения и сборке |

Списки сортируются детерминированно, поэтому повторные запуски дают одинаковый
вывод. Фильтры применяются к готовой модели данных, а не передаются внутрь
платформенного API, поэтому один и тот же фильтр означает одно и то же на всех
платформах.

## Команды

`nselecttrace --help` покажет список команд, а
`nselecttrace <команда> --help` — флаги конкретной команды.

### interfaces

Показывает все сетевые интерфейсы в порядке возрастания индекса интерфейса: имя,
состояние up/down, MAC-адрес и все назначенные адреса с длиной префикса.
Показываются и IPv4, и IPv6; отсутствующее значение выводится как `-`.

```console
$ nselecttrace interfaces
NAME              STATE  MAC                ADDRESSES
Loopback          UP     -                  127.0.0.1/8
                                         ::1/128
Ethernet          UP     00:11:22:33:44:55  192.168.1.42/24
                                         fe80::1234:5678:9abc:def0/64
Wi-Fi             DOWN   66:77:88:99:aa:bb  -
```

`--verbose` добавляет индекс интерфейса, MTU и признак loopback или
point-to-point:

```console
$ nselecttrace interfaces --verbose
Ethernet  (regular)
  index:      12
  state:      UP
  mac:        00:11:22:33:44:55
  mtu:        1500
  addresses:  192.168.1.42/24
              fe80::1234:5678:9abc:def0/64
```

### ports

Показывает занятые и слушающие сокеты локальной машины: протокол, локальный
адрес, состояние TCP, PID и имя процесса. У UDP нет машины состояний, поэтому
UDP-сокет выводит `-` в колонке STATE, а не придуманное `LISTENING`.

```console
$ nselecttrace ports
PROTO  LOCAL ADDRESS      STATE        PID    PROCESS
TCP    0.0.0.0:135        LISTENING    1200   svchost.exe
TCP    0.0.0.0:445        LISTENING    4      System
TCP    127.0.0.1:3000     LISTENING    8212   node.exe
TCP    192.168.1.6:5432   ESTABLISHED  9144   postgres.exe
UDP    0.0.0.0:53         -            1400   <unknown>
```

```bash
nselecttrace ports                      # все занятые и слушающие сокеты
nselecttrace ports --tcp                # только TCP
nselecttrace ports --udp                # только UDP
nselecttrace ports --port 8080          # только этот локальный порт
nselecttrace ports --pid 1234           # только сокеты этого процесса
nselecttrace ports --process node       # по имени процесса, без учёта регистра
nselecttrace ports --state LISTENING    # только это состояние TCP
```

### connections

Показывает **активные** соединения — сокеты, у которых есть удалённый endpoint.
Это и есть отличие от `ports`, где перечисляются занятые и слушающие сокеты.

```console
$ nselecttrace connections
PROTO  LOCAL              REMOTE                 STATE        PID    PROCESS
TCP    127.0.0.1:52143    127.0.0.1:3000         ESTABLISHED  8212   node.exe
TCP    192.168.1.6:52341  142.250.74.14:443      ESTABLISHED  8416   chrome.exe
TCP    192.168.1.6:53122  192.168.1.10:22        TIME_WAIT    0      <unknown>
TCP    [fe80::1234]:53126 [2607:f8b0::1]:443     ESTABLISHED  8416   chrome.exe
```

Удалённые адреса остаются адресами: `connections` не преобразует их в имена и не
отправляет пакетов. Адреса IPv6 заключаются в квадратные скобки, чтобы двоеточия
внутри адреса нельзя было спутать с разделителем порта.

```bash
nselecttrace connections                     # все активные соединения
nselecttrace connections --state ESTABLISHED # одно состояние TCP
nselecttrace connections --remote-port 443   # всё, что общается с портом 443
nselecttrace connections --tcp               # только TCP
nselecttrace connections --udp               # UDP-соединения, у которых есть peer
nselecttrace connections --process chrome    # по имени процесса
nselecttrace connections --pid 8416          # по идентификатору процесса
```

`--state` принимает состояния TCP, которые действительно можно наблюдать:
`CLOSED`, `LISTENING`, `SYN_SENT`, `SYN_RECV`, `ESTABLISHED`, `FIN_WAIT1`,
`FIN_WAIT2`, `CLOSE_WAIT`, `CLOSING`, `LAST_ACK`, `TIME_WAIT` (без учёта
регистра). Неизвестное состояние — это ошибка, а не пустой результат.

### dns

Прямое DNS-разрешение: имя хоста превращается в адреса, которые вернул системный
резолвер, и каждый адрес помечается семейством.

```console
$ nselecttrace dns example.com
HOST         TYPE  ADDRESS
example.com  A     93.184.216.34
example.com  AAAA  2606:2800:220:1:248:1893:25c8:1946

Resolved  : 2 records (1 A, 1 AAAA)
Duration  : 24.7ms
```

- **Только A и AAAA.** Именно эти записи возвращает резолвер Go. MX, TXT, CNAME,
  SRV и остальные не запрашиваются и не обещаются.
- **Только прямое разрешение.** Обратного (PTR) запроса нет. Если в качестве
  хоста передан IP-адрес, он уходит в резолвер как обычный ввод.
- **`--timeout`** ограничивает запрос, значение по умолчанию — `5s`.
- **Неудачный запрос — это ошибка.** Ошибка резолвера выводится как ошибка и
  завершает работу с ненулевым кодом; она никогда не показывается как успешный
  пустой результат. Если запрос прошёл, но записей нет, выводится
  `No records found` и код возврата `0`.
- `Duration` — время самого вызова резолвера, без разбора аргументов и вывода.

```bash
nselecttrace dns example.com
nselecttrace dns example.com --timeout 5s
nselecttrace dns example.com --timeout=500ms
```

```console
$ nselecttrace dns example.invalid
nselecttrace: failed to resolve "example.invalid": lookup example.invalid: no such host
```

### ping

Отправляет ICMP echo-запросы и показывает время отклика на каждый ответ.

```console
$ nselecttrace ping localhost --count 2
HOST       ADDRESS    SEQ  STATUS  TIME
localhost  127.0.0.1  1    OK      0µs
localhost  127.0.0.1  2    OK      0µs

Sent     : 2
Received : 2
Lost     : 0
```

```bash
nselecttrace ping localhost                 # четыре echo-запроса
nselecttrace ping 1.1.1.1 --count 3         # три echo-запроса
nselecttrace ping localhost --timeout 5s    # ограничить весь запуск
nselecttrace ping example.com --timeout=500ms
```

- **`--count`** по умолчанию равно `4`. Значение `0` или меньше — ошибка
  использования; непрерывного режима нет.
- **`--timeout`** по умолчанию равно `5s` и ограничивает весь запуск. Отдельный
  запрос, на который не ответили в пределах более короткого лимита на пакет,
  даёт строку `TIMEOUT`, и запуск продолжается: частичные потери показываются, а
  не прерывают всё целиком.
- **Один адрес на запуск.** Имя хоста может разрешаться в несколько адресов;
  проверяется ровно один, выбранный детерминированно (сначала IPv4, затем IPv6,
  наименьший адрес внутри семейства). Выбранный адрес виден в колонке ADDRESS.
- **Потери пакетов — не ошибка.** Завершённый запуск с потерями — это нормальный
  результат и код возврата `0`. В строке с таймаутом в колонке TIME стоит `-`:
  время отклика не выдумывается.

```console
$ nselecttrace ping 192.0.2.1 --count 2
HOST       ADDRESS    SEQ  STATUS   TIME
192.0.2.1  192.0.2.1  1    TIMEOUT  -
192.0.2.1  192.0.2.1  2    TIMEOUT  -

Sent     : 2
Received : 0
Lost     : 2
```

- **Доступность ICMP зависит от окружения.** В Windows и macOS ICMP обычно
  разрешён обычному пользователю. В Linux, как правило, нужны права root или
  `ping_group_range`, покрывающий пользователя. Если сокет открыть не удалось,
  так и написано в ошибке, а stdout остаётся пустым, вместо того чтобы показать
  выдуманный результат.
- Ctrl-C немедленно прерывает запуск, и прерывание сообщается как отмена, а не
  как потеря пакетов.

### about / version

```console
$ nselecttrace about
nselecttrace
Network diagnostic utility

host:    MY-HOST
runtime: windows/amd64
version: 0.1.0

$ nselecttrace version
nselecttrace 0.1.0
```

`version` показывает версию релиза, коммит Git и время сборки. Они подставляются
на этапе сборки через `-ldflags` (см. `internal/buildinfo` и `Makefile`), поэтому
бинарник, собранный прямо из исходников, покажет `unknown` для коммита и времени
сборки.

## Примеры

```bash
# Какие интерфейсы есть у машины и какие у них адреса?
nselecttrace interfaces

# Что слушается и какой процесс этим владеет?
nselecttrace ports --state LISTENING

# Общается ли сейчас что-нибудь с портом 443?
nselecttrace connections --remote-port 443

# Разрешается ли это имя по DNS и как быстро?
nselecttrace dns example.com

# Доступен ли хост по ICMP и с какой задержкой?
nselecttrace ping 1.1.1.1 --count 3

# Всё, чем владеет один процесс
nselecttrace ports --process node
```

## Коды возврата

Одно и то же соглашение действует для всех команд.

| Код | Значение |
|---|---|
| `0` | Успех, включая пустой результат и запуск ping с потерями пакетов |
| `1` | Ошибка выполнения: операцию не удалось выполнить |
| `2` | Ошибка использования: неверная командная строка |

Код `2` покрывает отсутствие хоста, лишний аргумент, неизвестный флаг, неверный
порт, неверное количество, неверное состояние и неверный `--timeout`. При коде
`2` в stderr всегда выводится подсказка по использованию, и операция не
выполняется. Код `1` покрывает ошибку резолвера, невозможность открыть
ICMP-сокет, отсутствие платформенного backend и таймаут или отмену. Сообщения об
ошибках содержат префикс `nselecttrace:` ровно один раз.

## Поддержка платформ

| Команда | Windows | Linux | macOS |
|---|---|---|---|
| `interfaces` | ✅ | ✅ | ✅ |
| `ports` | ✅ | ❌ не реализовано | ❌ не реализовано |
| `connections` | ✅ | ❌ не реализовано | ❌ не реализовано |
| `dns` | ✅ | ✅ | ✅ |
| `ping` | ✅ | ✅ | ✅ |

`ports` и `connections` опираются на платформенный backend перечисления сокетов.
В Windows этот backend использует IP Helper API. На платформе, где backend не
реализован, эти команды сообщают
`nselecttrace: ports are not implemented on this platform` и завершаются с кодом
`1`; они не выводят пустую таблицу, которую можно было бы принять за «ничего не
слушается».

У `connections` своего backend нет: он читает те же данные о сокетах через слой
`ports`, поэтому команда становится доступной на платформе сразу, как только это
сделает `ports`, и две команды не могут разойтись в описании одного сокета.

Все команды собираются для `windows`, `linux` и `darwin` и для `amd64`, и для
`arm64`. Для `ping` возможность собрать программу — это отдельный вопрос от
разрешения открыть ICMP-сокет, которое зависит от прав и сетевой конфигурации,
описанных выше.

## Установка

### Из исходников

Требуется Go 1.23 или новее.

```bash
git clone <repository-url>
cd nselecttrace
go build -o nselecttrace ./cmd/nselecttrace
```

URL репозитория показывает `git remote -v`. Отмеченного тегом релиза и формул
пакетных менеджеров пока нет, поэтому установка выполняется из исходников.

### Через инструменты Go

Когда модуль будет опубликован по своему окончательному пути импорта:

```bash
go install nselecttrace/cmd/nselecttrace@latest
```

### Windows

Сборка такая же, на выходе получается `nselecttrace.exe`:

```powershell
go build -o nselecttrace.exe ./cmd/nselecttrace
.\nselecttrace.exe ping localhost
```

### Linux и macOS

```bash
go build -o nselecttrace ./cmd/nselecttrace
./nselecttrace interfaces
```

В Linux команды `ports` и `connections` пока не реализованы, а `ping` может
потребовать повышенных прав.

## Разработка

```bash
go build ./...        # собрать всё
go run ./cmd/nselecttrace
go test ./...         # запустить тесты
go vet ./...          # статические проверки
gofmt -l .            # проверка форматирования (ничего не должна вывести)
```

`Makefile` объединяет типовые задачи, включая сборку с подстановкой версии,
коммита и времени сборки и кросс-компиляцию:

```bash
make build        # ./nselecttrace с версией, коммитом и датой
make test
make vet
make fmt-check
make cross        # кросс-компиляция для windows/linux/darwin
make release      # шесть релизных целей с подставленной версией
```

### Выпуск релиза

Релиз делается отправкой тега версии. Workflow в
`.github/workflows/release.yml` запускается только на тег вида `v*`, собирает
шесть комбинаций платформа/архитектура, подставляет версию, коммит и дату
сборки через `-ldflags` и прикладывает архивы к релизу на GitHub:

```bash
git tag v0.1.0
git push origin v0.1.0
```

Имена архивов: `nselecttrace-<тег>-<os>-<arch>.<zip|tar.gz>`, например
`nselecttrace-v0.1.0-windows-amd64.zip`. Версию, которую показывает
`nselecttrace version`, берут из тега без ведущей `v`.

### Структура проекта

```text
nselecttrace/
├── cmd/
│   └── nselecttrace/     # package main: единственная точка входа
├── internal/
│   ├── buildinfo/        # версия, коммит, дата сборки (через -ldflags)
│   ├── cli/              # разбор аргументов, реестр команд, справка, коды выхода
│   ├── interfaces/       # сетевые интерфейсы
│   ├── ports/            # TCP/UDP-сокеты (единственный источник данных о сокетах)
│   ├── connections/      # соединения = сокеты с удалённым endpoint
│   ├── processes/        # pid -> имя процесса
│   ├── dns/              # прямое DNS-разрешение
│   └── ping/             # доступность по ICMP
├── go.mod
├── LICENSE
├── README.md
├── README.ru.md
└── .github/
    └── workflows/        # workflow релиза (запускается на тег v*)
```

### Принципы устройства

- **Сбор данных не живёт в интерфейсе.** Каждый пакет в `internal/*` возвращает
  обычные структуры Go. CLI, будущий TUI и вывод JSON используют одни и те же
  значения:

  ```text
  системные API / сеть  ->  internal/*  ->  cli
  ```

  Команда никогда не вызывает системный или сетевой API напрямую.
- **Команды добавляются независимо.** Команда — это значение в реестре
  `cli.Command`. Чтобы добавить новую, не нужно трогать `main.go`.
- **Различия платформ выражены явно.** Там, где важна ОС, файлы с build-тегами
  стоят за одним платформенно-нейтральным API. Внутренности Windows не протекают
  в CLI, и в CLI нет проверок `GOOS`.
- **Ошибки классифицируются, а не угадываются.** Таймауты и отмены определяются
  через `errors.Is`/`errors.As` по sentinel-ошибкам контекста, а не сопоставлением
  текста ошибок.
- **Неподдерживаемое — это явная ошибка.** Платформа без backend сообщает об этом
  прямо; ни одна команда не выдумывает данные, чтобы выглядеть полной.

## Состояние проекта

nselecttrace — ранняя версия open-source проекта.

Текущий релиз v0.1.0 сфокусирован на:

- просмотре сетевых интерфейсов;
- локальных портах;
- активных соединениях;
- DNS-разрешении;
- ICMP ping.

Для перечисленных команд реализация завершена и покрыта тестами: у каждой команды
есть модульные тесты, граница с платформой покрыта тестами на фикстурах, а весь
проект собирается и проходит `vet` для Windows, Linux и macOS на `amd64` и
`arm64`. Команды, для которых на платформе нет backend, честно сообщают об ошибке,
а не деградируют молча.

## Планы

Будущие релизы могут расширить возможности диагностики и поиска неполадок сети.
Возможные направления, без определённого порядка и без обязательств:

- backend для Linux и macOS, чтобы `ports` и `connections` работали не только в
  Windows;
- дополнительные статистики ping, например min/avg/max времени отклика;
- проверка доступности по TCP и трассировка маршрута;
- более богатый вывод DNS, например запрос типов записей помимо A/AAAA.

Ничего из этого списка не является обещанием, и ни один интерфейс под это не
зарезервирован.
